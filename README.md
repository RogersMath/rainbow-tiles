# Rainbow Tiles: an engineering post-mortem from Claude

**Unicorn Sugarworld: Rainbow Tiles** — js13kGames 2026, theme "Unicorns and Rainbows".
Final build: 13,262 bytes zipped against a 13,312-byte limit. Single `index.html`, no
dependencies, no network, no storage.

I wrote most of the code. Jesse Rogers designed the game, playtested it, and made every
call that mattered. This document is about how it changed shape seven times and what each
change cost, because the interesting part of this project was not the code — it was
discovering that four separate systems had been quietly lying to us.

Written for people who want to build this kind of thing by hand.

---

## 1. What the game is

Nineteen hexagons in a radius-2 board. Each one starts as raw pink sugar, `[230, 175, 195]`
in RGB. Each has a target colour. A tile is "set" when every channel is within 35 of its
target. You cast spells that shift **one channel** on a hex footprint — a single tile, a
ring of six, or an "egg" (centre at full, ring at half strength).

Cards are drawn three at a time from a deck you build between rooms. Seven rooms, each
dominated by one colour of the spectrum. Fifteen tiles of nineteen and the floor is
accepted.

That description took four complete redesigns to arrive at.

---

## 2. Measure before you decide anything

The first version was 18,504 bytes zipped. The limit is 13,312. It was 39% over and
would have been rejected at submission.

That was not the interesting part. The interesting part is that the author believed it
fit, because a previous version had, and nobody had re-measured after adding content.

**The first thing I built was not a feature. It was a build script that prints the byte
count and exits non-zero when it's over.**

```js
const n = +execSync('stat -c%s dist/rainbow-tiles.zip').toString().trim();
console.log(`zip : ${n} / 13312 (${(n/13312*100).toFixed(1)}%) headroom ${13312-n}`);
if (n > 13312) { console.log('OVER BUDGET'); process.exit(1); }
```

Six lines. It ran after every single change for the rest of the project, and it caught
the budget going red four separate times — including once when I added a three-second
cutscene that put us 760 bytes over and I had to go find the bytes.

If you are building to a size limit, the number is the only thing that is true. Estimates
are worthless. "It's mostly comments, it'll compress" is worthless. Print the number.

### The pipeline that pays for your features

Source layout was three files concatenated at build time:

```
src/index.html   ← shell with /*__CSS__*/ and /*__JS__*/ placeholders
src/style.css
src/game.js
build.mjs        → dist/rainbow-tiles-dev.html   (commented, readable, playable)
                 → dist/index.html               (minified)
                 → dist/rainbow-tiles.zip        (submission)
```

Two outputs from one source is the important bit. The commented version is what you read
and debug and hand to judges who want to see the source; the minified version is what
ships. You never edit the minified file, so it can never drift.

Minification was terser (`passes: 3`, `unsafe: true`, `toplevel: true` mangling) plus
html-minifier-terser plus clean-css. Comments cost nothing — 53KB of commented source
minified to 35KB, and gzip does not care about the comments you already stripped. **Write
as many comments as you want. They are free.**

What we could *not* verify: `advzip` (Zopfli recompression, typically 3–8%) and
Roadroller (a context-mixing JS packer, often another 15–20%) both failed to run in the
build container. That left the project sitting at 50 bytes of headroom for the last three
turns, which is not headroom, it's a rounding error. If you are doing this seriously,
get those two working *first*, because they decide whether your remaining work is
comfortable or a knife fight.

## 3. Guarantee solvability by construction, not by tuning

The single most useful architectural decision in the whole project, and it was in the
original version before I touched it.

The board starts at pink. The target is generated by **casting real spells at the pink
board**:

```js
function makeTarget(R) {
  const t = HEX.map(() => PINK.slice());
  for (let k = 0; k < R.sp; k++) {
    const ch = pick(channelLottery(R));
    const shape = pick(shapeLottery(R));
    const pw = MAGS[ri(R.mg)];
    const at = pick(pool);
    const amt = (rnd() < BIAS ? R.dir[ch] : -R.dir[ch]) * pw;
    cast(t, at, shape, ch, amt);
    if (at !== MIRROR[at]) cast(t, MIRROR[at], shape, ch, amt);  // symmetry
  }
  return t;
}
```

Because the target was *built* by legal moves, a sequence of legal moves reaching it
provably exists. You never have to test whether a generated puzzle is solvable, and you
can never ship an impossible one.

This generalises far beyond colour puzzles. If your levels are procedural and your
verification is "run a solver and throw away the failures," you are paying compute to
recover a property you could have had for free by generating backwards from the solution.

Two refinements we needed on top:

**Mirroring.** `cast()` is applied at both a position and its mirror through the centre.
Without it, procedural targets looked like noise. With it, they look designed. One line,
enormous perceptual payoff. Random arrangements read as broken; symmetric arrangements
read as intentional.

**Reachability vs. speed.** Once the shop existed, generating targets from the *player's
current deck* seemed obvious — but it collides with fixed colour rooms (a Blue room can't
dodge blue because you didn't buy blue). We solved it differently: the starting deck is
twelve ±50 single-tile cards covering all three channels, and since the worst residual
against a 50-step is 25 while tolerance is 35, **that deck can reach any target given
enough rounds**. Upgrades buy *speed*, never *access*. No purchase path can lock you out
of a floor. That property is worth designing around explicitly rather than hoping for.

## 4. The bug that made four systems lie at once

This is the one to remember.

The board's error function used each tile's **worst** channel:

```js
const err = i => {
  let e = 0;
  for (let c = 0; c < 3; c++) e = Math.max(e, Math.abs(board[i][c] - target[i][c]));
  return e;
};
const totalErr = () => { let s = 0; for (let i = 0; i < 19; i++) s += err(i); return s; };
```

That is correct for deciding whether a tile is *set* — tolerance is per-channel, so a
tile is finished when its worst channel is inside 35.

It is catastrophically wrong as a measure of **progress**. Consider a tile that needs
R−50 and G−50. Cast R−50: red is now perfect, green is still off by 50, the max is still
50, `totalErr` does not move.

Four systems consumed that number:

1. **The floating feedback after a cast.** The player fixes a channel correctly and sees
   `±0`. The game tells them their correct move did nothing.
2. **`handHelps()`**, which decides whether the hand is dead. It returned `false` — hand
   is useless, sweep it — while holding exactly the card the player needed.
3. **Praline's tutorial hint**, which fires off `handHelps()`. The mentor recommends
   paying sugar to discard a good hand.
4. **My balance simulator**, whose greedy solver picked moves by `totalErr` reduction. It
   refused to make progress on any multi-channel tile.

Number four is how we found it. Jesse authored a hand-made tutorial floor — a unicorn
head in candy hexes — and my solver reported it failing: 14.4 tiles average against a
threshold of 15, 0% perfect. The floor looked fine. I changed the solver's metric to
sum all three channels and re-ran:

```
                        max-per-tile    summed
perfect rate (400 runs)      0%           93%
avg tiles set              14.4          18.9
worst run                    12            17
```

The floor was always fine. The metric was broken, and it had been broken in the shipped
game for weeks — hitting hardest on exactly the new tutorial, because the horn, the eye,
and one mane segment are all multi-channel tiles.

The fix is one line: sum every channel in `totalErr`, and leave `seated()` using max.

**The general lesson.** A single scalar was serving as (a) the win condition, (b) player
feedback, (c) an AI heuristic, and (d) a test oracle. Those four things have different
requirements, and reusing one number for all of them meant a single wrong choice
corrupted the player's understanding, the mentor's advice, and my own measurements
simultaneously — while every individual system looked correct in isolation.

If you take one thing from this document: **write down what each metric in your game is
for, and check that the same number is actually appropriate for each consumer.** Set-ness
is a max. Progress is a sum. They are not the same question.

## 5. Where agency lives is more important than how much there is

The redesign that taught me the most.

Version one gave the player, at cast time: 19 tiles × 9 spell types × 3 intensities ×
2 signs. Enormous freedom. Jesse playtested it and said it was too easy — "no
overshooting, you always have what you need, rarely are you undoing progress."

He was right, and my first instinct was wrong. I assumed the fix was tightening numbers.
The actual problem was structural: **wide move sets are always solvable.** Every element
of freedom I handed the player at the moment of action removed a constraint, and
constraints were the game.

The fix was not to remove agency. It was to **relocate it**:

| | Version 1 (cast time) | Final (purchase time) |
|---|---|---|
| Sign | free toggle, any cast | fixed when you buy the card |
| Magnitude | dial, any cast | fixed when you buy the card |
| Which spell | any owned spell | whatever you drew, 3 of them |

Total decisions went *up*. But they moved from a moment of pressure with perfect
information to a moment of calm with perfect information — the shop. A deck full of
+110 eggs bulldozes and overshoots; a deck of ±50 singles is surgical and too slow for
the late rooms. That is a real build decision, and it makes a bad hand *your fault* rather
than the shuffle's.

**Discrete, never continuous.** An intermediate version let the player dial a level-3
card down to any lower value. Jesse asked for it because of a genuine playtest
frustration ("I need 40 and my only card is 150"). I pushed back, because an arbitrary
dial makes overshoot *impossible* and overshoot was the game's main source of difficulty.
We landed on discrete steps — a level-3 card casts at 50, 80, or 110, your pick. The
frustration went away; the tension survived. Later the whole dial was replaced by
fixed-value cards, which is the same principle taken further.

When a playtester reports frustration, the report is data and the proposed fix is a
hypothesis. Fix the frustration. Do not necessarily fix it the way they suggested.

## 6. Anti-frustration systems stack, and the stack eats your stakes

The original had, simultaneously:

- `drawOne` weighted the deck toward useful cards at 2.2× and away from harmful ones at
  0.015×
- `guaranteeUsable` then swapped cards until half the hand was live
- A hint system, on by default, showing the sign of every channel error
- Unlimited free "Relay this floor" buried two taps deep in the settings menu

Each is defensible alone. Together they meant a player who always cast the biggest useful
card would do well without understanding anything, and could never actually lose.

We deleted the first two entirely and replaced them with one visible, priced valve:
**Sweep** — discard your hand, draw three more, costs a round and costs sugar on an
escalating curve (2, 2, 2, 4, 6, 8… resetting each floor). Relay costs two commendation
stars, and if you can't pay, the run ends.

The design principle: **one honest, visible price beats three invisible mercies.** A
player who sees "this costs you ◆4" is making a decision. A player being secretly
protected by a weighted shuffle is being managed.

A related detail Jesse insisted on: sweeping **wipes the undo history**. Otherwise you
could fish for a good hand and then rewind the fishing, which makes the sugar cost
fictional. Any resource cost that a rewind can refund is not a cost.

## 7. Simulate, and read the distribution rather than the average

I wrote a headless balance simulator that imports the game's real constants and functions
out of the source file, so it can never drift from the shipped tuning:

```js
const src = readFileSync('src/game.js', 'utf8');
const head = src.slice(0, src.indexOf('/* ===...\n   STATE + SCORING'));
const G = new Function(head.replace('"use strict";', '') + `
  return { PINK, TOL, ACCEPT, MAGS, PRICE, ROOMS, HEX, cast, makeTarget, srand, shuf,
           get deck(){return deck}, set deck(v){deck=v}, newRun, drawHand };`)();
```

The trick is that all the pure logic — grid, constants, `cast()`, target generation —
lives above a marker comment in the file, with no DOM access. Everything below the marker
touches the DOM. Slicing at the marker gives you the model without the view, from the
real source, with zero duplication.

Then a greedy solver plays 300 runs with a plausible purchase policy and reports:

```
full clears: 136/300 (45%)
failures by room: { 2:24  3:22  4:40  5:34  6:26  7:18 }
avg tiles set: 18.8  17.6  17.4  16.9  16.6  16.6  16.9
perfect rate: 87%  44%  33%  26%  19%  35%  44%
```

**The clear rate was never the useful number. The failure distribution was.** Two examples:

*Curve sag.* At one point rounds had been raised generously for the last two rooms.
Clear rate looked fine at 44%. The distribution showed failures of `R4:55 R5:50 R6:8
R7:9` — the two middle rooms were more than five times deadlier than the finale. The
"floor they will dance on" barely resisted. Four number changes fixed the shape while
leaving the overall rate identical at 45%.

*Ceiling detection.* An early build had the solver clearing 90% at 19/19 tiles in nearly
every room. That is not "well balanced," that is "the rounds budget is not binding" —
the puzzle was solvable in far fewer moves than granted, so the solver just walked to
the answer. The fix was raising commission density, not cutting rounds.

Two honest caveats about solver-based tuning:

- **A greedy solver with perfect error information is not a human.** It sees exact
  channel deltas on all 19 tiles and evaluates every card against every tile every turn.
  Real clear rates run lower. Use it for *shape*, not for absolute difficulty.
- **A bad policy makes the game look harder than it is.** My purchase policy buys the
  cheapest affordable card repeatedly, so its deck bloats to 40+ cards and dilutes. A
  player who buys selectively and uses the burn option should beat it. That gap is real
  skill headroom the sim can't measure — but you should know the gap exists rather than
  reading the sim's number as the truth.

## 8. The dead-half-deck problem

Jesse found this one, and it was the most important balance bug in the project.

Rooms were **one-way**. The Red room pushed R up, G down, B down — always. Purchases came
as ± pairs (both signs of a card enter the deck together). Therefore in any given room,
**half of every pair you bought was dead weight**, along with half your starting deck.

The consequence is worse than "some cards are bad." It means *buying made your deck
worse*: every purchase added one useful card and one blank, diluting the draw. The shop
was a trap, and I had not noticed across three revisions.

The fix is a single scalar. Each room still leans on its channels, but every channel is
pushed **both ways** across the floor:

```js
const BIAS = .65;   // ~2 pushes with the colour for every 1 against
const amt = (rnd() < BIAS ? R.dir[ch] : -R.dir[ch]) * pw;
```

At 1.0 the off-sign half of the deck is dead and shopping is a trap. At 0.5 the rooms stop
reading as colours at all. 0.65 keeps the identity and keeps both signs live.

**The general shape of this bug:** a constraint in one system (one-way rooms) silently
invalidated half the content of another system (paired purchases). Neither system was
wrong on its own. This class of bug is invisible to unit tests and to code review, and
visible almost immediately to a player who notices they're not enjoying shopping.

## 9. Author your tutorial. Do not roll it.

Room one was procedural like the rest. Because early rooms have low commission density
and tolerance is generous, a rolled first room frequently arrived **already at 15/19** —
the accept threshold — before the player cast anything. The tutorial taught nothing
because there was nothing to do.

Jesse replaced it with a hand-authored floor: a unicorn head in candy hexes, keyed by
axial coordinate.

```js
const UNIFLOOR = {
  '2,-2':  [230, 225, 145],   // horn — gold
  '1,0':   [180, 125, 195],   // eye — mulberry
  '0,2':   [230, 175, 145],   // muzzle — peach
  '0,-2':  [230, 125, 195],   // mane — hot pink
  '-1,-1': [230, 175, 145],   // mane — peach
  '-2,0':  [180, 225, 195],   // mane — mint
  '-2,1':  [230, 175, 245]    // mane — lilac
};
```

Every entry is one or two ±50 steps from pink, so the starting deck lays it. Seven tiles
off, ten casts needed, sixteen rounds granted. It teaches the mechanic, it delivers the
theme in the first thirty seconds, and Praline's opening line becomes "The Assembly
ordered a unicorn" instead of "that floor is the wrong colour."

Procedural generation is for volume. Your first level is not volume — it is the only level
most people will ever see, and it has a specific job. Hand-build it.

## 10. Techniques worth stealing

### Hex grids, cheaply

Axial coordinates. Nineteen tiles is `|q| ≤ 2, |r| ≤ 2, |q+r| ≤ 2`:

```js
const HEX = [];
for (let q = -2; q <= 2; q++)
  for (let r = -2; r <= 2; r++)
    if (Math.abs(q + r) <= 2) HEX.push({ q, r });

const px = h => [S * Math.sqrt(3) * (h.q + h.r/2), S * 1.5 * h.r];
const dist = (a,b) => (Math.abs(a.q-b.q) + Math.abs(a.r-b.r)
                     + Math.abs(a.q+a.r-b.q-b.r)) / 2;
const ADJ    = HEX.map(h => HEX.map((_,j)=>j).filter(j => dist(h, HEX[j]) === 1));
const MIRROR = HEX.map(h => idx[(-h.q) + ',' + (-h.r)]);
```

Adjacency and mirroring fall out of the distance function. No hand-written neighbour
tables, no special cases at the board edge. Roughly 300 bytes for the entire grid system.

### Clamping as a mechanic

Channels clamp at 0 and 255, and that destruction is permanent — no opposite spell
recovers it. This started as a rendering necessity and became the primary source of
difficulty. It also produced an unplanned difficulty curve: single-channel rooms pin the
other two channels at 0 or 255, which makes **overshoot in the pinned direction free**.
Red, Green and Blue rooms are forgiving without any code that makes them forgiving.
Indigo and Violet need mid-range values on two channels at once and forgive nothing.

The colour wheel *is* the difficulty curve. We did not design that; we noticed it and
then ordered the rooms to exploit it. Watch for emergent structure in your own systems
before you build an explicit difficulty knob.

### Legibility: make finished work recede

The board's job is to show you what is left to do. So:

- **Set tiles** desaturate to 50% opacity with a hairline stroke, and carry a small star
  in their commissioned colour so the pattern still reads.
- **Unset tiles** keep full contrast, get a white ring, a target swatch, channel chevrons,
  and numbers.

The eye goes straight to the work remaining, with no explicit "highlight the next move"
system. Attention direction by *de*-emphasis is cheaper and less patronising than
emphasis.

A related bug worth naming: exact numbers were printing for *every* channel including
ones already inside tolerance, so tiles read `R0 / G+65 / B0`. Two thirds of the text
said "this is fine" while burying the one number that mattered. Only render the values
that are actionable.

### Procedural audio with no sample data

Karplus-Strong plucked strings, rendered into an `AudioBuffer` at note time:

```js
function ks(freq, dur, damp, bright) {
  const sr = AC.sampleRate, n = Math.max(2, Math.round(sr / freq));
  const len = Math.ceil(sr * dur);
  const buf = AC.createBuffer(1, len, sr), out = buf.getChannelData(0);
  const line = new Float32Array(n);
  let last = 0;
  for (let i = 0; i < n; i++) {                 // filtered noise excitation
    const w = Math.random() * 2 - 1;
    last += (w - last) * bright;
    line[i] = last;
  }
  let p = 0, prev = 0;
  for (let i = 0; i < len; i++) {               // the delay line + lowpass
    const cur = line[p];
    line[p] = (cur + prev) * .5 * damp;
    prev = cur; out[i] = cur; p = (p + 1) % n;
  }
  return buf;
}
```

A noise burst in a feedback delay line whose length sets the pitch and whose lowpass sets
the decay. About 400 bytes for an instrument.

Song data is packed one character per eighth note, base-36 indexing a scale array, with
`.` for rest and `-` for hold:

```js
bass: '0--2--2--1--4--3--1--2--0--4--4--2--1--3--0--2--',
mel:  '7--9-8' + '7--5--' + '6--8-7' + '6--4--' + '9--8-6',
```

Scheduling is a `setInterval` at 25ms that pushes notes into Web Audio's own clock a
quarter-second ahead. **Never schedule audio off `setInterval` timestamps directly** —
JS timers drift audibly. Use the timer only to decide *when to queue*, and give Web Audio
absolute `currentTime` values for the actual note starts.

Every musical layer is gated on one scalar — tiles set / 19 — so the score thickens as
the floor fills. One number, and the music becomes a readout of game state.

Late in the project I traded the convolution reverb (a generated noise impulse response)
for a feedback delay line with a lowpass, to buy 83 bytes. At this tempo the ear reads it
as roughly the same room. That was the only real quality regression in the whole project.

### Share your assets, then dress them

The celebration needed a crowd of dancing unicorns. The mentor portrait was a separate,
elaborately drawn unicorn. Together they were 780 bytes over budget.

The fix: **one body, two dressings.** `UNI` is the shared path markup. The crowd instances
it through an SVG `<symbol>` and five `<use>` elements with different scales and
`hue-rotate` filters. Praline is the same figure with spectacles, a lighter mane and a
desaturate filter over it.

He now looks like his own students, which is better characterisation than the separate
drawing was — and it fit. When you're out of space, look for two things that are secretly
the same thing.

## 11. Testing a browser game without a browser

I could not open a browser. Everything I knew came from two tools.

**jsdom for logic and wiring.** Load the built file with `runScripts: 'dangerously'`,
stub the SVG geometry jsdom lacks, then drive it with synthetic events:

```js
w.SVGSVGElement.prototype.createSVGPoint = function () {
  return { x: 0, y: 0, matrixTransform: () => ({ x: 100, y: 100 }) };
};
w.SVGSVGElement.prototype.getScreenCTM = () => ({});
const click = s => d.querySelector(s)
  .dispatchEvent(new w.MouseEvent('click', { bubbles: true }));
```

Six small scripts — smoke, celebration, seeded sugar, briefings, keyboard, metric — ran
after every build. They found real bugs:

- **`Music.boot()` threw when Web Audio was blocked, and the throw took the whole start
  handler with it.** The title screen never dismissed. The game was completely unreachable
  for any judge with audio restricted, and it would have been invisible in normal testing.
  Wrap optional subsystems so they can never prevent the game from starting.
- **`$('ovbtn').onclick = postMortem`** passed the click Event as the `won` argument.
  Every loss displayed the victory text.
- **The result overlay (z-index 30) covered the dialogue box (z-index 20)**, so the
  entire ending monologue played invisibly behind a panel. A playtester caught this one
  before my tests did.
- Tapping the dialogue box before any dialogue existed threw on an undefined queue.

**A rasterizer for art.** I spent three rounds "fixing" Praline's SVG by adjusting
coordinates I could not see, and made him no better. Then I installed cairosvg and
rendered the paths to PNG:

```py
cairosvg.svg2png(url='/tmp/mentor.svg', write_to='mentor.png',
                 output_width=340, background_color='#2b1b2e')
```

The horn and tail were floating entirely free of the body. A grey mane path ran diagonally
across the barrel, and another landed on a hind leg. Ten minutes of looking beat three
rounds of reasoning. **If you are generating vector art programmatically, render it and
look at it. Coordinate arithmetic is not a substitute for eyes.**

**And the honest limit.** jsdom has no layout engine. It confirms elements exist; it says
nothing about whether a 3×2 grid fits at 380px, whether a blur transition looks like
anything, or where the disco ball actually lands. Every layout problem in this project was
found by Jesse's screenshots and none by my tests. If you're working headless, a
collaborator with a real device is not a nice-to-have — they are the only source of truth
about the thing your players will actually see.

## 12. Byte economics

When the celebration put us 760 over, I did not guess at what to cut. I measured each
candidate independently:

```
cut the reverb IR       →  83 bytes
cut the Ledger stats    → 119 bytes
cut the mentor portrait → 782 bytes
```

Only one was big enough, and it was the one I least wanted to lose. That measurement is
what motivated the shared-unicorn refactor — knowing the exact price of each option
turned a panic into a design problem.

Later, a dead-code sweep found 283 bytes of corpses from earlier redesigns still in the
file: a `<button id=sign>` and `<span id=pows>` from the cast-time UI that three
revisions had orphaned (and which were still rendering an orphan "+" next to the sweep
button), CSS for a list-shaped shop that no longer existed, a `SHAPES` constant, and a
`RUN.tiles += 0` no-op.

**When you redesign a system, the old system's DOM and CSS do not delete themselves.** A
periodic audit — every id in the HTML with no JS reference, every CSS selector with no
producer — is nearly free and it found more bytes than any clever optimisation.

For contrast, here is what content actually costs at this scale:

| Feature | Bytes |
|---|---|
| Three-second celebration (disco ball, 5 dancers, floor light show) | ~600 |
| Full keyboard support + discoverable key labels | 172 |
| Two-room shop preview + once-per-session briefings | 24 |
| A hand-authored tutorial floor | ~250 |
| Seeding the run with starting sugar | 0 (absorbed by slack) |

The cheap features were the ones that mattered most. The two-room preview closed a real
planning gap for 24 bytes; the celebration cost 25× that for a moment of spectacle.

## 13. Process notes

**Rate before you change.** Every redesign in this project started with an explicit
numeric rating across separated axes — theme fit, legibility, decision depth, size
discipline — rather than an overall verdict. Averaging them would have hidden the real
information. "Craft 8, legibility 4" tells you what to work on. "Overall 6" does not.

**Separate the axes when they diverge, and state the verdict plainly.** Version one was
genuinely well-crafted *and* genuinely illegible in its first two minutes. Both true,
neither cancelling the other.

**Decide in numbered lists.** Design questions went out as `1. A/B/C/D` and came back as
"1B, 2A, 3 none of these — what I actually want is…". Enormously faster than prose
negotiation, and the "none of these" option is where the best answers came from. The
colour-themed rooms, the ± pairs, and the authored tutorial were all Jesse rejecting my
menu and proposing something better.

**Push back once, properly, then commit.** I argued against the unlimited dial and against
a flat sweep price. Both arguments changed the design for the better. I also argued
against importing the WebGL unicorn from another project — that one was just a cost
report, and it redirected to a much cheaper SVG solution that reused what the file already
had.

**My own errors, for calibration.** I missed the one-way-room / paired-purchase
interaction across three revisions. I set the initial round budgets so loosely that a
greedy solver cleared 90% of runs at perfect scores. I shipped the max-per-tile progress
metric and it corrupted four systems. And at one point I confidently reported a byte
measurement taken from the wrong uploaded file. Every one of those was caught by either a
simulation or a screenshot — never by reading the code again.

## 14. Summary of transferable lessons

1. **Print the number.** A build script that measures and fails is the first thing you write.
2. **Generate levels backwards from the solution** so solvability is structural, not tested.
3. **Mirror your procedural output.** Symmetry is what makes generated content read as designed.
4. **Audit every metric against every consumer.** Set-ness is a max; progress is a sum. One number cannot serve four purposes.
5. **Move agency, don't add it.** Choices at the moment of action remove constraints. Choices before the action create builds.
6. **Discrete, not continuous.** A slider removes the failure mode your difficulty depends on.
7. **One visible price beats three invisible mercies.** Stacked anti-frustration systems delete your stakes.
8. **Read the failure distribution, not the clear rate.** And know your solver is not a human.
9. **Author your first level.** Procedural generation is for volume; level one is not volume.
10. **Look for the thing that's secretly one thing.** Two elaborate unicorns became one shared body plus two dressings.
11. **Render your generated art and look at it.** Coordinate reasoning is not eyes.
12. **Sweep for dead code after every redesign.** Orphaned DOM and CSS are the cheapest bytes you will ever find.
13. **Headless testing finds logic bugs and cannot find layout bugs.** Get a real device in the loop.
14. **Comments are free.** Minify at build time and write as many as you want.
